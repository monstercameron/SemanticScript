# Contract Stability

This page records the process contracts that are easy to lose in day-to-day
edits.

## Agent Contract

`AGENTS.md` and `CLAUDE.md` are mirrored root contracts. They must carry the
same SemanticScript rules; only the sentence that names the peer file should
differ. Treat the pair as versioned by the repository commit plus the active
`sem.version.v1` payload. When an agent-facing rule changes, update both files
and the changelog in the same change.

## JSON Schemas

`sem version --json` emits `emittedSchemas`, a machine-readable list of every
`sem.*.vN` schema the binary can return, plus `schemaManifest.stable` and
`schemaManifest.provisional`.

Policy:

- `*.v1` schemas are stable within a release line. Additive fields are allowed.
- Removing or changing the meaning/type of a field requires a new schema suffix.
- `*.v0` schemas are provisional and may change, but the changelog must call out
  behavior that agents are likely to depend on.
- Every release note section should mention added, removed, or renamed `sem.*`
  surfaces.

## Diagnostic Codes

Diagnostic codes are stable identifiers. Do not reuse a retired code for a new
meaning. If a diagnostic is replaced, keep `sem explain OLD_CODE --json`
actionable for at least one release by pointing to the replacement.

`sem reference --json` emits a `diagnosticIndex`; entries include a stable doc
URL under `docs/reference/diagnostic-codes.md#<lowercase-code>`.

## Syntax Rows

Syntax row status changes are compatibility events. Moving a row between
`Impl'd`, `Partial`, `Not impl'd`, `Proposed`, or metadata/refined categories
requires:

1. updating `docs/reference/syntax-inventory.md`;
2. updating parser/linter/editor support where relevant;
3. adding or adjusting focused tests;
4. calling out the status movement in `CHANGELOG.md`.

Doc code blocks should either be executable `semanticscript` examples that pass
the fenced-block check, or prose/`text` examples whose surrounding paragraph
states the status (`lowered`, `metadata`, `sync-fallback`, `partial`, or
`refined`).

## Release Notes And Channels

Tagged stable releases use tag/version names. Main-branch prereleases use the
`main-<SHORT_SHA>` channel naming used by `sem self latest --channel main` and
the compiler-exe workflow. Release manifests are generated by the release
workflow and carry artifact checksums; until `sem verify-release` exists, release
owners verify checksums from the attached manifest.

VSIX packages keep `publisher: semanticscript-local` until a Marketplace
publisher is assigned for 1.0. Release notes are generated from commit ranges;
if a release needs curated notes, write `release-notes-<tag>.md` alongside the
release prep before publishing.
